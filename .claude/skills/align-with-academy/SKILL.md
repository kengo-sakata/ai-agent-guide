# align-with-academy

ガイドの「書き方」を、Anthropic自身が初心者向けに書いた教材と突き合わせて磨くためのスキル。

## 守備範囲

| 扱う | 扱わない |
| --- | --- |
| 専門用語の噛み砕き方 | 記述が事実として正しいか |
| 説明の順序・構成 | 情報が最新か（機能名・コマンドの変更等） |
| 具体例・たとえ話の質と量 | リンク切れ・出典の妥当性 |
| 初心者がつまずく段差 | 章構成そのものの再設計 |

事実の誤りや古い記述に気づいたら、**直さずに報告だけする**。レポート末尾の「スコープ外メモ」に「表現ではなく事実の問題なので `maintain-guide` で確認してください」と添えて置く。表現レビューの最中に事実確認を始めると、どちらも中途半端になるため。

**1回の実行で扱うのは1章（＝`## 2-5.` のような節）まで。** 複数節を一度に見ると、指摘が浅く広くなって採否を判断しづらいレポートになる。

## 進め方

### 1. 対象を確定する

依頼文に節が書かれていれば（「章②のMCP」など）、対象を一行で宣言してそのまま進む。書かれていなければ、`docs/02_Claudeの機能一覧.md` の見出し一覧を出してどの節かを聞く。

対象が決まったら、その節の**重要度ラベル**（🔴必須／🟡よく使う／🟢知っておくと便利）を確認する。🔴の節は初心者が最初に読む前提なので、指摘の基準を一段厳しくする。🟢の節は必要になった人が調べに来る場所なので、多少密度が高くても許容範囲。

### 2. ガイド側を、初めて読む人の頭で読む

対象節を通しで読み、**自分がその機能を知らなかったら、どの行で手が止まるか**を先にメモする。Academyを見た後だと「Academyにあってこちらに無いもの」しか目に入らなくなるので、順序が大事。

### 3. Academy側を読む

`references/academy-map.md` に章とコース・レッスンの対応表とURL規則がある。まずそれを読む。

読むときは**原文を手元に持ち込まない**。WebFetch には「本文を再現して」ではなく、こう聞く：

> この節はどんな順序で説明を組み立てているか。専門用語を最初に出す前に何を置いているか。どんなたとえ話・具体例を使っているか。読者に何を知っている前提で書かれているか。

返ってくるのが要約であること自体が、後述の引き写し防止に効く。

対応するAcademyコンテンツが見つからない、あるいは扱いが薄い場合は、**無理に比較しない**。「対応するAcademyコンテンツが見当たらなかった」と報告してその節はスキップし、代わりにガイド単体で読みやすさのレンズだけをかける（それも価値がある）。

### 4. 差分を洗い出す

以下のレンズを順にかける。全部を毎回使う必要はないが、少なくとも上3つは必ず見る。

- **未定義の専門用語** — 初出の用語に説明が付いているか。章①や他節に説明があるなら参照が張られているか。「stdio」「OAuth」「プロンプトインジェクション」のように、当部門の読者でも人によって既知度が割れる語に注意
- **難易度の段差** — 前の段落から次の段落で、前提知識が急に上がっていないか。特に「一言でいうと」の平易さから本文の密度への落差
- **具体例の不足** — 抽象的な説明が、読者の日常業務に接地しているか。Academyは「まず困りごと、次に用語」の順を取ることが多い。ガイドが逆順になっていないか
- **説明の順序** — 「なぜ必要か → 何であるか → どう使うか」になっているか。いきなり手順から入っていないか
- **一文の長さと情報密度** — 一文に注意事項が3つ以上詰まっていないか。箇条書きの各項目が長すぎないか
- **図と本文の役割分担** — 図が本文の言い換えになっていないか。図を見ずに本文だけで通じるか

### 5. 改善案を提示して、そこで止まる

**本文を編集しない。** 提案として出し、ユーザーが1件ずつ採否を決めてから、採用分だけを反映する。ここで先回りして直すと、ユーザーは「どこが変わったか」の差分読解から始めることになり、レビューの負荷が上がる。

提案は**多くても5〜8件**に絞る。優先度の低い指摘まで並べると、重要な2〜3件が埋もれる。

粒度は**1提案＝1つの差し替え箇所**。連続した範囲に複数の問題が重なっているなら（用語も未定義だし図とも重複している、など）1提案にまとめる。観点ごとに割ると、ほぼ同じ差し替え案を2回書くことになって採否を判断しづらい。逆に、離れた行の問題は観点が同じでも別提案にする。

提案に載せるか「軽微なため省いた点」に落とすかは、**読者が理解を誤るか、そこで止まるか**で切る。そうなるなら優先度が低くても差し替え案まで書く。読み心地の問題にとどまるなら軽微に落とし、一行挙げるだけにする。

## 改善案を書くときの2つの制約

### 制約1：Academyの文章を引き写さない

**一文でも、ほぼそのままでも、翻訳しても駄目。** 参考にしてよいのは「表現のアイデア」だけで、文そのものではない。

ガイドは日本語、Academyは英語なので「訳せば別物」と錯覚しやすいが、**構文と論理展開をなぞった訳文は引き写しに当たる**。ここが一番の落とし穴。

借りてよいもの／駄目なものの線引き：

| 借りてよい | 借りてはいけない |
| --- | --- |
| 説明の順序（困りごと→用語→手順、など） | 段落の構成をそのままなぞること |
| 「たとえ話を置く」という判断 | そのたとえ話そのもの |
| どの読者層を前提に書くかの水準 | 言い回し・文のリズム |
| 用語（MCP、stdio、`claude mcp add` 等の固有名詞・コマンド） | 用語の定義文 |

固有名詞やコマンド名が一致するのは当然で、引き写しではない。問題になるのは**説明の文**。

出力する前に、改善案を一つずつ見て「これはAcademyの文の言い換えになっていないか、自分がガイドの文脈から書き起こした文か」を確認する。判断に迷う案は出さない。

### 制約2：ガイドの声を消さない

このガイドはAcademyとは読者も目的も違う。**SI業務で複数顧客案件を掛け持つ部門メンバー**が読者で、「技術的に可能なことと、やってよいことは別」という判断軸が随所に埋め込まれている。契約上の注意喚起、章④への参照、国内事例のケーススタディは、Academyには存在しないこのガイド固有の価値。

「読みやすくする」を口実にこれらを削らない。Academyに合わせて平板にするのではなく、**Academyの噛み砕き方を借りて、ガイド固有の内容をより通じやすくする**のが目的。改善案が注意喚起や事例を削る方向に働いていたら、それは間違った方向の案。

同様に、既存の書式（`**一言でいうと**`、`**こんな時に使います**`、`**紛らわしい機能との違い**` といった見出しパターン、`**重要度：**` ラベル）は章全体で揃っているので、単節の都合で崩さない。

## レポートの形

```markdown
## 対象

章② §2-5. MCP（Model Context Protocol）／重要度：🟡よく使う
参照したAcademyレッスン：
- Claude Code 101「MCP」
- Introduction to Model Context Protocol「Introducing MCP」「MCP clients」

## 総評

（3〜5行。初めて読む人がこの節のどこで止まりそうか。全体として何が効いていて、何が足りないか）

## 改善提案

### 提案1：（一言タイトル）
**観点**：未定義の専門用語 ／ **優先度**：高
**該当**：docs/02_Claudeの機能一覧.md:195-199

**現状**
> （ガイドの現文をそのまま引用）

**気になる点**
（初心者の目線で、何が分からないか）

**Academyでの扱い（アイデアの出所）**
（どういう順序・どういう例を使っているか。1〜2行。原文の訳ではなく、手口の説明）

**改善案**
（差し替え案の全文。そのまま貼れる形で）

### 提案2：…

## 軽微なため省いた点

- （一行ずつ）

## スコープ外メモ

- （事実・鮮度に関わる気づき。「表現ではなく事実の問題なので `maintain-guide` で確認してください」を添える）
- （対応するAcademyコンテンツが見当たらなかった項目があればここに）

## 採否

| # | 提案 | 優先度 | 採否 |
| --- | --- | --- | --- |
| 1 | … | 高 | |
```

「現状」は必ずガイドの原文を引用する。改善案だけ見せられても、ユーザーは元の文を探しに行くことになる。

**「Academyでの扱い」の欄は、対応する扱いがあった提案にだけ置く。** 手順2でガイドを先に読んだ段階で見つかる問題（同じ警告が繰り返されている、図と本文が同じことを言っている等）は、Academy側に対応物が無いことがある。それは比較に失敗したのではなく、ガイド固有の問題を見つけたということなので、欄ごと省いてそのまま提案に載せる。**Academyは指摘の出所の一つであって、指摘してよい条件ではない。**

## レビュー後

ユーザーが採否を返したら、採用分**だけ**を反映する。却下された案の趣旨を別の形で混ぜ込まない。反映は最小限の差分にとどめ、周辺の文を「ついでに」整えない。

反映後、変更した節をもう一度通しで読み、採用案どうしが衝突していないか（同じ説明が2箇所に増えていないか、削った語の参照が残っていないか）を確認する。

最後に、ファイル末尾の「改訂履歴」に1行追記する（`maintain-guide` と同じ形式・同じ場所）。**事実の更新ではないことが分かるように書く**。後から履歴を追う人が、記述内容が変わったのか書き方だけが変わったのかを判別できる必要がある。

```markdown
- 2026-09-10: §2-5 MCP の説明順序と用語の補足を改善（表現のみ、記述内容の変更なし）
```

**コミットはしない。** 差分はワーキングツリーに残し、ユーザーに確認してもらう。
