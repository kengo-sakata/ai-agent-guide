# ガイド文書の保守・更新

## このSkillが解こうとしている問題

このガイドは「Claude Codeで今なにができるか」を社内向けに説明する文書で、Claude Code
自体が数週間単位で変わっていくため、**書いた時点では正しかった記述が静かに古くなる**。
古い記述は、読者が実際にコマンドを叩いて失敗するまで気づかれない。

だからこのSkillの仕事は、文章をきれいにすることではなく、**個々の技術的な主張が今も
真かを一次情報源で確かめ、違っていたところだけを、出典付きで直す**ことにある。
「たぶん変わっていそう」で書き換えるのは、古い記述と同じくらい有害。確認できないものは
直さずに「要確認」として報告に回す。

## 対象範囲

範囲を厳しく絞るのは、レビューする人間が差分を追えるようにするため。

| 区分 | 対象 |
|---|---|
| 本文 | `docs/02_Claudeの機能一覧.md`、`docs/03_開発に役立つTips.md` |
| 図解 | 上記本文が参照する `docs/images/*.drawio.svg` |
| 教材 | `hands-on/` 配下の README・`*.sample`・`sample-project/` |

**対象外**(依頼されても、このSkillでは触らずに理由を伝える):

- `docs/01_AIエージェントとは何か.md` — 概念中心で変化が緩やかなため
- `docs/04_セキュリティ・ガバナンス.md` — 組織判断が入るため、Web上の情報をもとに
  自動修正してはいけない(気づいた点は報告のみ)
- `docs/00_はじめに.md`、`docs/index.md`、`docs/xx_企画書.md` — 本Skillの守備範囲外

**1回の実行で扱うのは、1ファイルまたは明示された1節とその関連ファイル一式まで。**
「②を全部見て」と言われても、勝手に全節へ広げず、どの節から始めるかを確認する。
節をまたいで気づいた問題は、直さずに報告の「次に見るべき箇所」に書く。

**章構成は変えない。** 見出しの追加・削除・並び替え、節番号の振り直し、節の統廃合は
このSkillの範囲外。既存の見出しの中身の正確性だけを保守する。
節を増やしたい・消したいという判断が必要になった場合は、そう報告して人間に委ねる。

ファイル配置・節と図解の対応表・ハンズオンとの対応は `references/repo-map.md` にある。
対象を決めたら最初に読むこと。

## 手順

### 1. 対象を確認する

どのファイルのどの節を対象にするかをユーザーに確認する。すでに明示されていれば、
その範囲を復唱して着手する(確認のために止まる必要はない)。
対象が広すぎる場合はここで絞る提案をする。

### 2. 主張を棚卸しする

対象節を読み、**検証可能な技術的主張**を一覧化する。拾うのは次のようなもの:

- 仕様・挙動(「Hooksは30種類以上のイベントに登録できる」)
- 数値(行数の目安、トークン数、上限値、価格、モデル名)
- 手順・コマンド例・設定ファイルのキー名やパス(`.claude/rules/`、`/permissions` 等)
- 製品名・機能名・提供状況(GA / プレビュー / 廃止)
- 「公式に推奨されている」という趣旨の記述 — 本当に公式が言っているかは要確認

意見・方針・社内ルール(「当部門ではCLI・デスクトップ・IDE拡張のみ」等)は検証対象外。
これらは組織判断であって、公式ドキュメントで真偽が決まるものではない。

一覧は、あとで差分判定の結果を書き込める形で作る(主張 / 現在の記述 / 根拠 / 判定)。

### 3. 一次情報源で裏を取る

`references/sourcing.md` に、公式ドキュメントのURL対応表と、
「何を一次情報源とみなすか」の基準を書いてある。**必ず読んでから調査を始める。**

要点だけ先に:

- **最初に `https://code.claude.com/docs/llms.txt`(全ページの索引)を引いて、
  正しいURLを確認する。** URLを推測で組み立てると、実在するが内容が違うページを
  一次情報源として引用してしまう(例:`/docs/en/iam` は404にならず別ページを返す)
- URL末尾に `.md` を付けると整形済みMarkdownが返るので、それを WebFetch する
- 節全体を棚卸しする場合は、先に changelog / What's new で「何が変わったか」を
  押さえるほうが速い(`git log -1 --format=%ad -- <file>` で本文の最終更新日が分かる)
- 公式ドキュメントで確認できない場合に限り WebSearch で補足を探す
- **ブログ・SEO記事だけを根拠に本文を書き換えない。** 実測値や体験談としてなら引用可
  だが、その場合は「ある実測例では」「〜と報告されています」のように、公式の断定と
  区別できる書き方にする(既存本文がこの書き分けをしているので踏襲する)

### 4. 差分を判定する

各主張を4つに仕分ける。

| 判定 | 意味 | 対応 |
|---|---|---|
| 現状のまま | 一次情報源と一致 | 触らない |
| 更新が必要 | 仕様・数値・名称が変わった | 書き換える(出典必須) |
| 廃止された | 機能・手順が無くなった | 現行の代替に書き換える(出典必須) |
| 要確認 | 一次情報源で確定できない | **本文は触らず**報告に載せる |

「要確認」を本文に反映しないのがこのSkillの一番大事な線引き。
迷ったら「要確認」に倒す。

### 5. 本文を更新する

- 古い・誤った記述は**書き換える**。旧記述をコメントや注記で残す必要はない
  (Gitで履歴が追えるため、残すとかえって読みにくくなる)
- **修正内容には必ず出典URLを付ける。出典を示せない修正は本文に反映せず、
  報告の中で提案として書くに留める**
- 数値や仕様の変更は「いつの情報か」が分かる形にする
  (例:「2026年◯月時点の公式ドキュメントでは〜」)
- 既存の文体・敬体・記号の使い方(重要度の🔴🟡🟢、`>` 引用での注意書き、
  「**参考**：[ページ名](URL)（Anthropic公式ドキュメント）」の形)を崩さない
- 節の分量バランスを大きく変えない。1文の訂正で済むところを段落追加で解決しない

### 6. 関連ファイルの追随を確認する

本文を直したら、同じ事実を書いている他の場所も一緒に直さないと矛盾が残る。

1. **図解** — その節が参照する `.drawio.svg` の内容が古くなっていないか確認する。
   **確認を始める前に `references/diagrams.md` を読む。** 直すと決めてからではなく
   確認の時点で読む理由は、そこに「そもそも自分で直すべきか、人間に委ねるべきか」の
   判断基準があるため。文字の差し替えで済むのか、座標調整が必要で手を出すべきでないのかは、
   基準を知らないと判断できない。
   これらのSVGは1ファイルの中に「描画用のテキスト」と「draw.io再編集用のソース」を
   **二重に持っている**ため、片方だけ直すと壊れる。手順書なしで編集しないこと
2. **ハンズオン** — `hands-on/` に対応する教材があれば、コマンド例・設定例・Skillの
   書き方が更新後の本文と矛盾していないか確認し、必要なら合わせて直す。
   どのディレクトリがどの節に対応するかは `references/repo-map.md` にある
   (ディレクトリ番号と節番号は1つずれているので、番号で突き合わせない)。
   対応する教材が無い節ならこの手順は不要で、その旨を報告に書く
3. **他の節・他の章からの相互参照** — 同じ数値や機能名が他所にも書かれていないか
   `grep` で確認する。対象外の章(①④)に古い記述を見つけた場合は、
   直さずに報告する

最後に、本文の体裁が崩れていないかを機械的に確認する。

```bash
python .claude/skills/maintain-guide/scripts/check_structure.py <更新したファイル>
```

②③の各節は章全体で要素の順序が揃っており(`**紛らわしい機能との違い**` が節の最後)、
参考リンクを足すときにこれを崩しやすい。1項目だけの箇条書きが段落の後に浮くと、
他の節と体裁が食い違う。`[ok]` を確認してから次に進む。

### 7. 改訂履歴に追記する

更新したファイルの末尾に、次の形式で追記する。

```markdown
## 改訂履歴

- 2026-09-10: MCPのツール定義トークン消費の記述を公式ドキュメント準拠に更新、図解04も追随
```

- セクションが無ければ、ファイル末尾(「まとめ」の後)に新設する
- 日付は実行日。1行で、何を直したかが分かるように書く
- 図解・ハンズオンを直した場合も、この1行の中に一言含める
  (図解やハンズオン側に別途履歴を作る必要はない)

### 8. レビュー用に整理する

**コミットしない。** 変更はワーキングツリー上の差分として残し、
コミット・マージするかどうかの判断は人間に委ねる。ブランチも切らない。
PNGなどの確認用中間生成物はリポジトリに置かない(一時ディレクトリに出す)。

`git diff --stat` で変更範囲を確認し、次の形式で報告する。

```markdown
## 対象
<ファイル / 節>

## 変更点
| # | 箇所 | 変更前 | 変更後 | 根拠(URL) |
|---|---|---|---|---|

## 変更しなかったが確認したもの
- <主張>: 一次情報源と一致(URL)

## 要確認(本文には反映していません)
- <主張>: <なぜ確定できなかったか> / <どう調べれば確定するか>

## 追随して直したファイル
- docs/images/xx.drawio.svg: <何を直したか>(整合チェック・目視確認 済)

## 次に見るべき箇所
- <今回の範囲外で気づいた点>
```

差分の量が少ない場合は表を箇条書きにしてよい。大事なのは
**「どこを、なぜ変えたか」と「変えなかった理由」が両方分かること**。

### 9. 人間のレビューを待つ

報告したら、そこで止まる。ユーザーが差分を見て判断する。
「コミットしておいて」と明示的に言われた場合のみコミットする。

## 表現の問題に気づいたとき

このリポジトリには姉妹スキル `align-with-academy` があり、そちらが「読みやすいか・
初心者に分かるか」を担当する。分担は次の通り。

| | 見るもの | 本文を編集するか |
| --- | --- | --- |
| `maintain-guide`(本スキル) | 事実として正しいか・古くないか | する(出典付きで) |
| `align-with-academy` | 読みやすいか・初心者に伝わるか | しない(提案のみ) |

**説明が分かりにくい・用語が唐突・例が足りないといった表現の問題に気づいても、
本スキルでは直さない。** 報告の「次に見るべき箇所」に
「表現の問題なので `align-with-academy` で検討してください」と添えて置く。
事実確認の最中に表現改善を始めると差分が混ざり、レビューする人間が
「これは事実の訂正なのか、書き方の好みなのか」を判別できなくなるため。

逆に、`align-with-academy` の実行中に事実の誤りが見つかって本スキルに回ってきた場合は、
その指摘を手順2の棚卸しリストに入れて、通常の手順で検証する。

## やらないこと

- 章構成の変更(見出しの追加・削除・並び替え・節番号の振り直し)
- 対象外ファイル(①④等)への書き込み
- 出典を示せない修正の本文反映
- 一次情報源で確認できていない「たぶん変わった」という推測での書き換え
- 依頼された範囲を超えたファイルへの波及修正
- コミット・ブランチ作成・プッシュ(明示的な指示がある場合を除く)
- 確認用PNGやスクラッチファイルのリポジトリへの追加
