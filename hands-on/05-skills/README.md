# ハンズオン05：繰り返す手順をSkill化する

対応するガイド：[② §2-6 Skills](../../docs/02_Claudeの機能一覧.md#2-6-skills)

## 目的

「APIエンドポイントを追加するときの手順」をSkillとしてファイルに書き出し、**2〜3個続けてエンドポイントを追加**します。

2回目・3回目に手順を説明し直さなくても同じ形で作られること＝**手順そのものが再利用できる**ことを体感するのが狙いです。

## 前提

- [hands-on/README.md](../README.md) の環境構築（手順1〜8）が完了していること
- 作業ディレクトリは `~/hands-on/sample-project`

---

## 手順

### 1. Skill を作成する

用意してあるサンプルを、Skillの置き場所にコピーします。

```bash
cd ~/hands-on/sample-project
mkdir -p .claude/skills/add-endpoint
cp ../05-skills/SKILL.md.sample .claude/skills/add-endpoint/SKILL.md
cat .claude/skills/add-endpoint/SKILL.md
```

`.claude/skills/<Skill名>/SKILL.md` という配置がSkillの形式です。ファイルの先頭には次のようなメタ情報（フロントマター）が入っています。

```yaml
---
name: add-endpoint
description: このプロジェクトにAPIエンドポイントを追加する。新しいAPIを作るとき、既存のAPIにエンドポイントを足すときに使う。
---
```

`description` は「**どういうときに使うSkillなのか**」をClaudeに伝えるための説明です。ここが曖昧だと、必要な場面でSkillが選ばれません。本文には、仕様の確認からテスト・検証までの手順が順番に書かれています。中身を一度読んでおいてください。

### 2. Skill が認識されているか確認する

```bash
claude
```

入力欄で `/` を1文字だけ入力すると、使えるコマンドの候補が一覧表示されます。その中に **`add-endpoint`** が出てくることを確認します（`description` に書いた説明も一緒に表示されます）。

### 3. 1つ目のエンドポイントを追加させる

```
/add-endpoint 完了済みのTODOをまとめて削除する
```

Skillの手順に沿って、仕様の提示 → `lib/store.ts` への関数追加 → `route.ts` の作成 → テスト作成 → `npm run typecheck` / `npm test` の実行、という流れで進むはずです。

途中で仕様の確認を求められたら答えてください。

### 4. 2つ目を追加させる（手順は説明しない）

**手順の説明はいっさいせずに**、次の依頼だけを出します。

```
/add-endpoint 指定したTODOを複製する
```

1つ目と同じ流れで進むことを確認します。

### 5. 3つ目を追加させる

```
/add-endpoint すべてのTODOを完了状態にする
```

### 6. 結果を確認する

Cloud Shell の別タブ（ターミナル上部の「+」）で差分を確認します。

```bash
cd ~/hands-on/sample-project
git status
git diff
npm test
```

3つのエンドポイントが**同じ形**（同じ配置ルール、同じエラー処理、テスト付き）で追加されているかを見てください。

### 7. コンテキスト消費を確認する（任意）

```
/context
```

Skillの本文は**使うときに読み込まれる**もので、CLAUDE.md のように常時コンテキストに載り続けるわけではありません（ガイド② §2-6 の progressive disclosure）。Skillが増えても、常時の消費は `description` の分だけに抑えられます。

---

## 確認ポイント

以下が見えたら成功です。

- [ ] `/` の候補一覧に `add-endpoint` が表示される
- [ ] 1つ目のエンドポイントが、Skillに書いた順番（仕様確認 → store → schema → route → テスト → typecheck/test）で作られている
- [ ] **2つ目・3つ目で手順を説明していないのに**、1つ目と同じ流れ・同じ形で追加されている
- [ ] 3つのエンドポイントのエラー処理・レスポンス形式・テストの置き場所が揃っている
- [ ] `npm test` が通り、追加したエンドポイント分のテストが増えている

## ひとことメモ：03（CLAUDE.md）との違い

どちらも「毎回説明し直さずに済む」ための仕組みですが、役割が違います。

| | CLAUDE.md（03） | Skill（05） |
|---|---|---|
| 書くもの | **規約・前提知識**（命名規則、エラー形式、コマンド） | **手順**（何をどの順番でやるか） |
| 読み込まれ方 | セッション開始時に常に読み込まれる | 必要と判断されたとき、または `/skill名` で呼ばれたときに読み込まれる |
| 効くところ | あらゆる依頼に対して一貫性が保たれる | その手順を踏む作業の再現性が保たれる |
| コンテキスト | 常時消費する（だから200行程度が目安） | 使うときだけ消費する |

**規約の一貫性は CLAUDE.md、手順そのものの再利用は Skill** と考えると使い分けやすくなります。CLAUDE.md が長くなってきたときに、複数ステップの作業手順をSkillへ切り出すのが公式にも推奨されている整理の仕方です。
