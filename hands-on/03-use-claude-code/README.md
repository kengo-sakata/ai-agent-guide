# ハンズオン03：CLAUDE.md の有無で応答がどう変わるか

対応するガイド：[② §2-4 Use Claude Code](../../docs/02_Claudeの機能一覧.md#2-4-use-claude-codeメモリセッションワークフロー)

## 目的

**まったく同じ依頼**を、CLAUDE.md が無い状態と有る状態で1回ずつ出し、出力の違いを自分の目で比較します。

「CLAUDE.md を書くと規約が守られやすくなる」という説明を、実際の差分として確認するのが狙いです。

## 前提

- [hands-on/README.md](../README.md) の環境構築（手順1〜8）が完了していること
- 作業ディレクトリは `~/hands-on/sample-project`
- 手順8で初期状態をコミットしてあること（1回目と2回目の間でコードを戻すため）

## 題材

「TODOの統計（総数・完了数・未完了数）を返すエンドポイントを追加する」という依頼を2回出します。

`sample-project` には既にエラーレスポンスの共通形式（`lib/api-error.ts`）とzodによる検証（`lib/schema.ts`）、`tests/` 配下のテストがありますが、**それらを使うべきという指示はどこにも書かれていません。**

---

## 手順

### 1. CLAUDE.md が無いことを確認する

```bash
cd ~/hands-on/sample-project
ls CLAUDE.md
```

`No such file or directory` と出ればOKです。

### 2. 1回目：CLAUDE.md なしで依頼する

```bash
claude
```

```
TODOの統計を返す新しいAPIエンドポイントを追加して。
総数・完了数・未完了数を返すもの。
```

完成したら、**何が出てきたかを記録します。** Cloud Shell の別タブ（ターミナル上部の「+」で開けます）で差分を確認してください。

```bash
cd ~/hands-on/sample-project
git status
git diff
```

次の観点で見てください。

| 観点 | 見るところ |
|---|---|
| **配置・命名** | どのパスに作られたか（`app/api/todos/stats/route.ts`？ 別の場所？）／関数名 |
| **レスポンス形式** | キー付きオブジェクトか、数値やフラットなJSONを直接返しているか |
| **データ操作** | `lib/store.ts` の関数を使ったか、`route.ts` の中で配列を直接操作したか |
| **エラー処理** | `lib/api-error.ts` のヘルパーを使ったか、独自形式のエラーJSONを作ったか、そもそもエラー処理が無いか |
| **テスト** | `tests/` にテストが追加されたか、されなかったか |
| **確認** | `npm run typecheck` や `npm test` を自分で実行したか |

**メモに残しておいてください。**（後で比較します）

### 3. 変更を元に戻す

セッションを終了します。

```
/exit
```

```bash
git restore .
git clean -fd
git status
```

`nothing to commit, working tree clean` になればOKです。

### 4. CLAUDE.md を追加する

用意してあるサンプルをコピーします。

```bash
cp ../03-use-claude-code/CLAUDE.md.sample ./CLAUDE.md
cat CLAUDE.md
```

命名規則・レスポンス形式・エラー処理の方針・テスト必須といった規約が書かれています。中身を一度読んでおいてください。

### 5. 読み込まれていることを確認する

CLAUDE.md はセッション開始時に読み込まれるため、**セッションを再起動します。**

```bash
claude
```

```
/context
```

`Memory files` の行が増えている（＝CLAUDE.md がコンテキストに載っている）ことを確認します。`/memory` で、読み込まれているメモリファイルの一覧も確認できます。

### 6. 2回目：まったく同じ依頼をする

```
TODOの統計を返す新しいAPIエンドポイントを追加して。
総数・完了数・未完了数を返すもの。
```

### 7. 1回目と比較する

手順2と同じ観点で、別タブから差分を見比べます。

```bash
cd ~/hands-on/sample-project
git status
git diff
```

## 確認ポイント

以下のような違いが見えたら成功です（どの項目に差が出るかは毎回同じではありません）。

- [ ] 1回目と2回目で、**エラーレスポンスの形式**が違う（2回目は `lib/api-error.ts` のヘルパーを使い、`{ "error": { "code", "message" } }` の形に揃っている）
- [ ] 1回目にはテストが無く、2回目には `tests/` にテストが追加されている
- [ ] 2回目は `npm run typecheck` と `npm test` を自分で実行してから完了報告している
- [ ] レスポンスのJSON構造・ファイル配置・関数名が、2回目は既存コードと揃っている
- [ ] `/context` で、CLAUDE.md が `Memory files` として常にコンテキストを消費していることが見える

## ひとことメモ

- CLAUDE.md は**セッション開始時に必ず読み込まれる**ため、「毎回説明しなくても前提が揃う」効果があります。一方で、書いた分だけ常にコンテキストを消費します（だから公式は1ファイル200行程度を目安としています）
- CLAUDE.md は**「説得」の層**です。「必ず」と書いても100%守られる保証はありません。確実に守らせたいことは Hooks（ガイド② §2-9）で仕組みとして組みます
- 今回はプロジェクト直下に置きましたが、`~/.claude/CLAUDE.md`（自分の全プロジェクト共通）、`src/frontend/CLAUDE.md`（モジュール固有）のように、スコープを分けて書けます
- **手順そのもの**を再利用したい場合は CLAUDE.md ではなく Skill が向いています。次の [05-skills](../05-skills/README.md) で扱います
