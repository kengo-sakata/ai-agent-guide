# ハンズオン02：コンテキストウィンドウを体感する

対応するガイド：[② §2-3 Core concepts](../../docs/02_Claudeの機能一覧.md#2-3-core-concepts基本概念)

## 目的

- コンテキストウィンドウが**有限**であることを、数字で確認する
- 同じ調査でも、**やらせ方によってメインセッションの消費量が変わる**ことを比較する
- あわせて Plan Mode・`/context`・`/compact`・`/clear` の基本操作に触れる

## 前提

- [hands-on/README.md](../README.md) の環境構築（手順1〜8）が完了していること
- 作業ディレクトリは `~/hands-on/sample-project`
- 手順8で初期状態をコミットしてあること（作業を元に戻すため）

## 題材

`sample-project` は入力検証に **zod の3系**を使っています。これを**4系に上げる**のが今回の作業です。

zod は 3→4 で検証エラーの取り出し方などが変わっているため、バージョンを上げただけでは `npm run typecheck` が通りません。「ライブラリを1つ上げて、影響箇所を探して直す」という、実務でよくある作業です。

---

## 手順

### 1. 作業前のコンテキストを確認する

```bash
cd ~/hands-on/sample-project
claude
```

セッションが開いたら、まず現在の状態を確認します。

```
/context
```

`System prompt` / `Tools` / `Memory files` / `Messages` / `Free space` といった内訳が表示されます（項目名や表示形式はバージョンによって異なります）。

**このうち `Free space`（空き）のパーセンテージをメモしておいてください。** これが比較の基準になります。

### 2. Plan Mode で「計画だけ」立てさせる

`Shift+Tab` を押してモードを切り替えます。入力欄の下の表示が `plan mode` になるまで押してください（通常 → 自動承認 → Plan Mode のように循環します）。

そのうえで、次のように依頼します。

```
package.json の zod を4系に上げたい。まずこのリポジトリのどこに影響が出るかを調べて、
修正方針を計画としてまとめて。zod の 3→4 の破壊的変更や非推奨APIも踏まえてほしい。
```

Plan Mode ではファイルの書き換えが行われません。調査と計画立案だけを行い、最後に「この計画で進めてよいか」を確認してきます。

**ここでは計画を承認しないでください。**「No, keep planning」を選ぶか `Esc` で抜けます。次の手順で通常モードからやり直します。

### 3. 「調査だけ」でどれだけ消費したかを見る

```
/context
```

**コードは1行も変わっていないのに、`Free space` が減っている**ことを確認します。減った分は、調査のために読み込んだファイルの内容と検索結果です。

### 4. 実際に修正させる

`Shift+Tab` で通常モードに戻し、次のように依頼します。

```
zod を4系に上げて。package.json を更新して npm install も実行し、影響のある箇所を直して。
最後に npm run typecheck と npm test が通ることを確認して。
```

ファイルの変更やコマンド実行の許可を求められたら承認してください。

> **さらに消費させたい場合**：続けて「zod公式のマイグレーションガイドも参照して、他に対応漏れがないか確認して」と依頼してみてください。Webから取得したドキュメントもコンテキストに載るため、消費量の増え方が分かりやすくなります。

### 5. 作業後のコンテキストを確認する

```
/context
```

手順1・手順3の数字と比べます。ファイル読み込み・コマンド実行結果・会話が積み上がって、空きが減っているはずです。

### 6. `/compact` で圧縮する

```
/compact
```

会話が要約されます。終わったらもう一度確認します。

```
/context
```

空きが回復していること、そして**会話の流れ自体は維持されている**（「さっき何を直したか」を聞けば答えられる）ことを確認してください。

---

### 7. 発展：調査をサブエージェントに任せて比較する

同じ調査を、最初から Explore サブエージェントに投げる2段階のやり方に変えて、メインセッションの消費量を比較します。

まず初期状態に戻します（別のターミナルタブ、またはセッションを抜けてから実行）。

```bash
cd ~/hands-on/sample-project
git restore .
git clean -fd
npm install
```

セッションに戻り、会話をリセットします。

```
/clear
/context
```

手順1と同じ初期値に戻っていることを確認したら、**調査だけ**をサブエージェントに任せます。

```
Explore サブエージェントを使って、package.json の zod を4系に上げた場合の影響箇所だけを
調査して。修正はまだしないで、影響のあるファイルと必要な変更内容の要約だけ報告して。
```

実行中、次のような行が表示されます。

```
Explore(zod v4 の影響箇所を調査)
  ⎿ Done (N tool uses · Xk tokens)
```

この `Xk tokens` は**サブエージェント側のコンテキストで消費された量**です。メインセッションには要約だけが返ります。

```
/context
```

手順3（メインセッションで直接調査させた場合）と比べてください。そのうえで、返ってきた要約をもとに修正させます。

```
その調査結果のとおりに修正して。npm run typecheck と npm test が通ることを確認して。
```

---

## 確認ポイント

以下が見えたら成功です。

- [ ] 作業の前後で `Free space` のパーセンテージが減っている
- [ ] **コードを変更していない「調査だけ」の段階でも**消費が増えている（＝調査そのものが枠を食う）
- [ ] `/compact` の後で空きが回復し、それでも会話の流れは維持されている
- [ ] Explore に調査を任せた場合、調査で使ったトークンはサブエージェント側で消費され、メインセッションの消費は手順3より小さい
- [ ] Plan Mode では、依頼しても実装が始まらない（計画の提示で止まる）

## ひとことメモ

- ここで見た「調査でコンテキストが埋まり、その後の実装の精度が落ちる」現象が、ガイド② §2-3 のケース1です。調査を切り出す価値は、この数字の差から来ています
- `/clear` と `/compact` はどちらも会話の整理ですが、`/clear` は完全リセット（別の作業に移るとき）、`/compact` は要約して圧縮（同じ作業を続けたいとき）という使い分けになります
