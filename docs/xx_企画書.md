1. 背景・目的
当部門ではSI業務(要求整理・見積り提案から要件定義〜リリースまで)において、AIエージェント(Claude Code、Codex等)の利用が現場で進んでいる。また、GitHub Copilot・Codexについても社内整備が予定されており、今後利用可能なツールは複数になっていく見込みである。一方で、
効率的な使い方(Tips・ベストプラクティス)が個人・チーム任せで標準化されていない
セキュリティ・ガバナンス上の懸念点(機密情報の入力、外部サービス連携、ログ管理等)が整理されておらず、現場の自主性に依存した状態になっている

5. ④セキュリティ・ガバナンスの検討方針(詳細)
④は本ガイドの中でも特に検討を重ねた部分であり、以下の考え方で整理している。
5.1 基本方針:ゼロトラスト的発想だが、完全な技術強制は目指さない
現場の自主性に委ねると目的達成が難しいため、可能な限り「仕組みで防ぐ」ことを志向する。ただし調査の結果、多くの観点は技術だけでは閉じず、行動原則(ガイド)による担保が必要であることが分かった。これは世の中の他社の公開事例(ガイドライン・チェックリスト中心の対策が主流)とも整合する結論である。
5.2 構成方針:抽象(やりたいこと)→具体(実現方法)の方法論として整理
GitHub Copilot・Codexの社内整備も予定されていることを踏まえ、④はツールを問わず通用する形で組み立てる。具体的には、各観点を**「達成したいこと(ツール非依存の目的)」→「現時点の実現方法(Claude Codeでの具体策)」**の2段構成で記載する。これにより、Copilot・Codexの提供が始まった際にも「目的」の行は変えずに「実現方法」の列を追加するだけで拡張できる、拡張性のある構成とする。
5.3 検討した観点と結論
達成したいこと(目的)	技術で対応可能か	現時点の実現方法(Claude Code)
個人情報・機密情報を送信しない	△部分的	全文の自動マスキングはコスト対効果が悪く、現場に工数負担をかけるため見送り。案件(契約)ごとにAI利用可否・入力可能情報の範囲を事前判定する運用を軸とする。判断基準は顧客のセキュリティ規約・自社のISC相談資料を用いる。補助として、hooks(UserPromptSubmit/PreToolUse)による構造化パターン(メールアドレス・マイナンバー等)の自動検知・自動置換は任意導入の選択肢として提示する(工数ゼロで実装可能だが、自然文の機密性までは検出できない限界がある)
貸与端末以外・私的利用禁止	△部分的	TeamプランはメールアドレスのみのOAuthで端末・NWの制約が技術的にかかっていない。SSO有効化が理想だが、全社クラウド基盤へのSSO統合は情報システム部門の体制上、現時点では困難。まずは行動原則として示唆し、将来的な組織課題として切り出す。軽量な代替として「ドメインキャプチャ」機能(ドメイン検証のみで完結する可能性がある)の情シスへの相談も選択肢として残す
ローカルへの追加インストール禁止	○可能	Claude Codeの実行に伴う不足アプリの自動インストール行為への対応として、devcontainer(開発コンテナ)での実行を推奨事項とする。ホスト側は資産のホワイトリスト運用を維持しつつ、コンテナ内では開発に必要なツールを自由に導入できるようにし、開発停滞と統制の両立を図る。ただしdevcontainer利用にはDocker Desktop等の環境構築が必要で、企業規模によっては有償ライセンスが発生する点は別途整理が必要(無償の代替構成も存在)
外部サービス(MCP)を勝手に操作しない	○可能	個別のMCP接続は認証情報が必要なため実行できないが、「どのMCPサーバーを追加登録できるか」自体の制限が本質的な対策となる。管理設定(managed settings)による許可リスト運用を推奨事項とする
誰が・どのエージェント・モデルで・何を生成したか	△部分的	Teamプランの管理コンソールでは利用者・リクエスト数・トークン消費量等は確認できるが、生成内容までは確認できない。内容込みの監査ログはEnterprise限定機能のため、現時点では利用実績の定期確認までを運用範囲とし、内容の監査は将来検討事項とする
上記はいずれも「目的」の行を変えずに、Copilot・Codexが導入された段階で「実現方法」列を追加すれば良い形になっている(例:Copilotの場合はCoding AgentがGitHub Actions VM内で動作しPRとして人間レビューを経る設計のため、一部観点はClaude Codeより統制しやすい可能性がある等、ツールごとに事情が異なる)。
